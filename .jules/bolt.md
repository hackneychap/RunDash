## 2025-02-18 - [SQLite Query Optimization for Garmin Data Sync]
**Learning:** The application syncs run activities from a local GarminDB SQLite database, which previously transferred thousands of old records into Python memory only to discard them based on a 2-year cutoff. Furthermore, date parsing using `strptime` is significantly slower compared to `fromisoformat`.
**Action:** When querying large local SQLite databases (like GarminDB), push down WHERE clauses to filter large datasets at the database level instead of in-memory. For date string parsing, use string slicing and `datetime.date.fromisoformat` over `datetime.datetime.strptime` where the string format allows (e.g., extracting "YYYY-MM-DD" from "YYYY-MM-DD HH:MM:SS").

## 2025-03-02 - [Django Query Optimization for block_list Dashboard View]
**Learning:** When performing complex aggregations over multiple one-to-many relationships in Django (like `RunActivity` and `BRace` relative to `TrainingBlock`), using standard `.annotate(Sum('activities...'))` with `Count('b_races...')` together can cause SQL JOIN fanout (Cartesian products) leading to incorrect or duplicate data results. Also, iterating in python over pre-fetched child relations consumes enormous memory when user has lots of activities.
**Action:** Use `Subquery` with `OuterRef('pk')` to calculate the aggregates inside isolated queries, and then use those in the `.annotate()` of the parent query. This pushes memory-intensive loops to the database level while avoiding cartesian products.
