## 2025-02-18 - [SQLite Query Optimization for Garmin Data Sync]
**Learning:** The application syncs run activities from a local GarminDB SQLite database, which previously transferred thousands of old records into Python memory only to discard them based on a 2-year cutoff. Furthermore, date parsing using `strptime` is significantly slower compared to `fromisoformat`.
**Action:** When querying large local SQLite databases (like GarminDB), push down WHERE clauses to filter large datasets at the database level instead of in-memory. For date string parsing, use string slicing and `datetime.date.fromisoformat` over `datetime.datetime.strptime` where the string format allows (e.g., extracting "YYYY-MM-DD" from "YYYY-MM-DD HH:MM:SS").
## 2024-05-18 - [Django Caching and Signals for Dashboard Performance]
**Learning:** The dashboard view performs multiple complex aggregations (`Sum`, `Avg`, `TruncWeek`, `TruncMonth`) on the `RunActivity` model, which can be computationally expensive on every page load as the data grows. Django's cache framework (`cache.set`, `cache.get`) is effective here, but bulk operations (`bulk_create`, `bulk_update`) used in background tasks bypass Django's standard `post_save` and `post_delete` signals.
**Action:** When caching database-heavy views, explicitly invalidate the cache using `cache.delete()` after `bulk_create` or `bulk_update` operations, in addition to using signals (`post_save`, `post_delete`) for standard model saves/deletes. This ensures cache consistency.
