## 2025-02-18 - [SQLite Query Optimization for Garmin Data Sync]
**Learning:** The application syncs run activities from a local GarminDB SQLite database, which previously transferred thousands of old records into Python memory only to discard them based on a 2-year cutoff. Furthermore, date parsing using `strptime` is significantly slower compared to `fromisoformat`.
**Action:** When querying large local SQLite databases (like GarminDB), push down WHERE clauses to filter large datasets at the database level instead of in-memory. For date string parsing, use string slicing and `datetime.date.fromisoformat` over `datetime.datetime.strptime` where the string format allows (e.g., extracting "YYYY-MM-DD" from "YYYY-MM-DD HH:MM:SS").

## 2023-10-25 - [Dashboard Caching and Signals Invalidation]
**Learning:** The dashboard view performs multiple complex database aggregations which are very expensive and lead to N+1 query patterns. Caching this data provides significant performance gains (~30x faster load times). However, since bulk operations like `bulk_create` and `bulk_update` (used during Garmin synchronization) bypass standard Django signals like `post_save` and `post_delete`, caching frameworks can fall out of sync unless explicitly handled. Additionally, cache timeouts should be dynamically calculated (e.g., seconds until local midnight) rather than static (e.g., 24 hours) for data that depends on "today" to avoid serving stale context.
**Action:** Always verify if database changes use bulk operations when relying on signals for cache invalidation. Explicitly clear relevant caches in task finalize methods where bulk operations are used. When caching relative dates, calculate expiration based on when the "relative date" next rolls over.
